Comprendre l'Architecture Réseau d'OPCP

On Premise Cloud Platform (OPCP) est livré sous forme d'une pile intégrée (serveurs, commutateurs, automatisation, plan de contrôle) installée directement dans vos locaux. Avant et pendant le déploiement, votre équipe doit comprendre comment OPCP s'interconnecte avec votre réseau d'entreprise : par où il communique, quels flux il émet, et quels services il consomme de votre infrastructure.

OPCP repose sur une séparation stricte entre deux réseaux ayant des rôles, des équipements et des usages très différents :

  • Le réseau de données (data plane) — transporte le trafic de vos charges de travail
  • Le réseau d'administration (Out-of-Band, OOB) — utilisé pour piloter la plateforme elle-même

Cette séparation est structurante : elle conditionne la sécurité, la résilience et la qualité de service de la plateforme.

Mode air-gap : OPCP est conçu pour fonctionner sans aucun accès Internet. Les seules destinations attendues sont les services de votre propre système d'information.

Niveaux de gestion

OPCP est proposé selon deux niveaux de délégation. Le niveau choisi détermine qui opère le plan de contrôle et donc quels flux d'interconnexion doivent être ouverts vers OVHcloud.

Mode Administration plateforme Opérations courantes Lien IPsec vers OVHcloud
Self-managed Client Client Non
Fully managed by OVHcloud OVHcloud OVHcloud Oui (IPsec)

Quel que soit le mode, vous restez responsable de tout ce que vous déployez au-dessus des services OPCP : machines virtuelles, conteneurs, instances bare-metal, applications, données métier et sauvegardes applicatives.

Le réseau de données (Data Plane)

Le réseau de données est emprunté par les charges de travail hébergées sur les serveurs OPCP (machines virtuelles, conteneurs, instances bare-metal exposées via OpenStack). Il transporte :

  • Le trafic applicatif entrant et sortant des instances
  • Les communications entre instances au sein de l'OPCP
  • Les flux entre OPCP et le reste de votre SI (bases de données, services internes, utilisateurs finaux)

Composants matériels

  • Interfaces data des serveurs — connectées aux commutateurs Top-of-Rack
  • Commutateurs Top-of-Rack (ToR) — paire redondée par baie (Arista DCS-7050CX3-32S)
  • Commutateurs edge (déploiements multi-baies) — jonction entre le réseau interne OPCP et votre réseau amont
  • Commutateurs spine (mode FABRIC) — interconnectent les ToR de plusieurs baies
  • Liens uplink fibre — 40 GbE ou 100 GbE vers votre Customer Upstream Data Network

Le réseau de données est piloté de bout en bout par OPCP via OpenStack Neutron : la création d'un réseau, d'un sous-réseau ou d'une règle de sécurité depuis Horizon ou l'API se propage automatiquement aux commutateurs sous-jacents.

Le réseau d'administration (Out-of-Band, OOB)

Le réseau OOB est le réseau par lequel OPCP s'administre lui-même et par lequel vous (et, en mode Fully managed, les équipes OVHcloud) accédez aux interfaces de gestion. Il est physiquement et logiquement séparé du réseau de données. Il porte :

  • L'accès aux API OpenStack, à l'interface Horizon et aux outils de gestion OPCP (HTTPS)
  • L'accès SSH aux OPCP Core Controllers (commandes opcp-cli, opcp-diag)
  • Les échanges inter-contrôleurs pour la résilience du plan de contrôle (synchronisation d'état, élection de quorum, bascule de la VIP)
  • La collecte de logs et de métriques émise depuis OPCP vers vos services internes
  • Les flux sortants vers vos services d'infrastructure (NTP, DNS, S3 de sauvegarde, LDAP, syslog)

Pas de communication transverse : Aucune communication directe n'est possible entre le réseau de données et le réseau OOB depuis l'intérieur d'OPCP. Toute communication transverse passe obligatoirement par votre réseau amont, ce qui vous laisse la maîtrise des règles de sécurité entre les deux périmètres.

Topologies de déploiement

OPCP est livré selon trois modes de déploiement, dimensionnés en fonction du contexte d'usage. Ils diffèrent principalement par le nombre de baies supportées et la résilience du plan de contrôle.

Mode Cas d'usage Plan de contrôle Baies Spine/Edge
NANOPOD Démo, sites distants, bureaux, edge Non résilient (1 contrôleur) 1 Non
MINIPOD Infrastructure résiliente compacte Résilient (3 contrôleurs) 2–3 Edges uniquement
FABRIC Déploiement datacenter complet Résilient (3 contrôleurs) 3–10+ Spine + Edges

NANOPOD — Configuration à 1 contrôleur

Éléments clés :

  • Serveurs — interfaces data connectées aux deux ToR ; BMC rattaché au switch de management
  • ToR A / ToR B — commutateurs Top-of-Rack redondés portant le réseau de données et remontant vers votre réseau amont (fibre 40/100 GbE)
  • Switch de management (mgmt) — agrège les BMC des serveurs et les ports de management des ToR
  • OPCP Core Controller — raccordé via un uplink OOB (25/10 GbE) vers votre réseau OOB amont, plus un port 1 GbE BMC

Note : Avec un seul contrôleur, il n'y a pas de redondance du plan de contrôle. Une panne matérielle interrompt l'administration de la plateforme (les charges de travail déjà déployées continuent de s'exécuter). Pour la production exigeant la haute disponibilité, retenez MINIPOD ou FABRIC.

MINIPOD / FABRIC — Configuration à 3 contrôleurs

Différences par rapport au NANOPOD :

  • 3 OPCP Core Controllers — chacun avec un uplink OOB 25/10 GbE et un lien BMC 1 GbE. Une IP virtuelle (VIP) partagée est utilisée pour atteindre les API OpenStack et Horizon
  • Commutateurs edge — s'intercalent entre les ToR et votre réseau amont. Le réseau de données est configuré sur les edges (pas sur les ToR)
  • Commutateurs spine (FABRIC uniquement) — interconnectent plusieurs baies ; couche megaspine au-delà de 10 baies

Intégration à votre environnement

L'intégration d'OPCP repose sur deux périmètres réseau que vous fournissez et gardez sous votre contrôle :

Customer Upstream Data Network

Votre réseau de production. OPCP s'y raccorde via les liens fibre des ToR (NANOPOD) ou des edges (MINIPOD/FABRIC) à 40 ou 100 GbE. La configuration des uplinks est pilotée par OPCP via une API exposée. Le contenu et la segmentation du réseau de données sont entièrement gérés par OpenStack Neutron.

Customer Upstream OOB Network

Le périmètre depuis lequel OPCP est administré. Vous devez y prévoir :

  • Un sous-réseau dédié à OPCP avec une passerelle par défaut
  • Une résolution DNS : un nom de domaine délégué à OPCP (ex : *.opcp01.exemple.com)
  • Des règles de filtrage autorisant les flux décrits dans la matrice
  • Un accès à au moins une source NTP (obligatoire)

Interconnexion OVHcloud (mode Fully Managed)

En mode Fully managed by OVHcloud, OVHcloud doit pouvoir atteindre votre réseau d'administration OPCP pour l'exploitation et le support à distance. Cette interconnexion repose sur un tunnel IPsec site-à-site avec les paramètres par défaut suivants :

  • IKEv2 uniquement (IKEv1 non supporté)
  • Authentification : Pre-Shared Key (PSK)
  • Chiffrement : AES-256
  • Hash : SHA-256
  • Groupe Diffie-Hellman 14
  • Perfect Forward Secrecy (PFS) activé

Une fois le tunnel établi, les équipes OVHcloud accèdent à votre OPCP uniquement via cette interconnexion — aucun accès direct depuis Internet n'est ouvert sur votre plateforme.

Points Clés à Retenir

  • OPCP dispose de deux réseaux strictement séparés : Réseau de données (trafic des charges de travail) et Réseau OOB (administration)
  • Aucune communication directe n'est possible entre les deux réseaux depuis OPCP — votre réseau amont contrôle tout trafic transverse
  • Trois topologies de déploiement : NANOPOD (1 baie, 1 contrôleur), MINIPOD (2–3 baies, 3 contrôleurs), FABRIC (3–10+ baies, 3 contrôleurs avec spine)
  • Le réseau de données est piloté par OpenStack Neutron et supporte les modes access, trunk (802.1Q) et QinQ (802.1ad)
  • OPCP est conçu pour fonctionner en mode air-gap — aucun accès Internet n'est requis
  • En mode Fully managed, OVHcloud se connecte via un tunnel IPsec (IKEv2, AES-256) à votre réseau OOB
